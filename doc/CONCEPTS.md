# Nodus Concepts

Этот документ фиксирует основные понятия Nodus.

Цель — использовать одни и те же термины при проектировании, разработке и обсуждении системы.

Документ описывает, что означает понятие, но не определяет окончательную техническую реализацию.

---

## Project

**Project** — проект, с которым работает Nodus.

Проект включает не только исходный код, но и контекст, необходимый для его понимания:

- структуру;
- исходный код;
- зависимости;
- архитектурные решения;
- существующие реализации;
- соглашения;
- политики;
- историю некоторых решений.

Nodus должен рассматривать проект как существующую систему, а не как набор независимых файлов.

---

## Knowledge

**Knowledge** — формализованное понимание проекта, доступное Nodus.

Knowledge может содержать:

- описание компонентов;
- назначение файлов и каталогов;
- связи между компонентами;
- архитектурные решения;
- существующие паттерны;
- доменные понятия;
- ограничения;
- исключения;
- другие сведения, полезные для работы с проектом.

Knowledge не является абсолютной истиной.

Она может быть неполной, устаревшей или ошибочной и должна иметь возможность уточняться.

---

## File Understanding

**File Understanding** — краткое структурированное описание того, как Nodus понимает конкретный файл.

Например:

- назначение;
- ответственность;
- ключевые зависимости;
- используемые компоненты;
- связанные файлы;
- важные особенности;
- потенциальные ограничения.

File Understanding позволяет не заставлять LLM каждый раз заново анализировать проект с нуля.

Это один из механизмов формирования Knowledge.

---

## Context

**Context** — информация, которую Nodus предоставляет модели для выполнения конкретной задачи.

Context может включать:

- саму задачу;
- релевантную Knowledge;
- похожие реализации;
- содержимое файлов;
- зависимости;
- Policies;
- результаты предыдущих действий;
- результаты проверок.

Context не должен автоматически содержать весь проект.

Главная задача Nodus — сформировать достаточный и релевантный контекст.

---

## Context Builder

**Context Builder** — компонент, который определяет, какая информация необходима модели для конкретной задачи, и формирует из неё Context.

Условный поток:

Task
↓
Relevant Knowledge
↓
Relevant Examples
↓
Relevant Files
↓
Policies
↓
Context

Context Builder является одним из ключевых компонентов Nodus.

---

## Example

**Example** — существующая реализация в проекте, которая может служить образцом для выполнения новой задачи.

Nodus должен отдавать предпочтение существующим примерам перед генерацией решений «с нуля».

Например:

> Добавить новую сущность по образцу существующей сущности.

Example не обязательно является идеальным или единственно правильным решением.

Он является свидетельством того, как подобные задачи уже решались в данном проекте.

---

## Policy

**Policy** — мягкое правило, предпочтение или рекомендация, описывающая желательное поведение в проекте.

Policies не должны без необходимости превращаться в жесткие ограничения.

Например:

> Предпочитать существующий механизм X вместо создания нового.

вместо:

> Использование любого другого механизма запрещено.

Исключения должны быть возможны.

---

## Model Adapter

**Model Adapter** — слой, скрывающий конкретную LLM от остальной системы.

Nodus должен иметь возможность работать с различными моделями.

Замена модели не должна требовать изменения основной логики Nodus.

Model Adapter отвечает за взаимодействие с конкретным провайдером или моделью.

---

## Tool

**Tool** — операция, которую Nodus может выполнить во внешней системе.

Примеры:

- чтение файла;
- поиск;
- изменение файла;
- работа с Git;
- запуск команды;
- запуск тестов;
- получение результата проверки.

Tools позволяют модели не только генерировать текст, но и взаимодействовать с проектом.

---

## Agent

**Agent** — компонент, который выполняет задачу через итеративный цикл принятия решений и использования Tools.

Условный цикл:

Task
↓
Model
↓
Tool
↓
Result
↓
Model
↓
Tool
↓
...

Agent не является всем Nodus.

Agent — один из механизмов выполнения задач внутри Nodus.

---

## Agent Runtime

**Agent Runtime** — инфраструктура, управляющая циклом выполнения Agent.

Runtime отвечает за:

- состояние задачи;
- вызовы модели;
- выполнение Tools;
- передачу результатов обратно модели;
- ограничения выполнения;
- завершение задачи;
- обработку ошибок.

---

## Verification

**Verification** — проверка результата работы Nodus.

Она может включать:

- компиляцию;
- тесты;
- линтеры;
- проверки проекта;
- анализ diff;
- Policies;
- другие автоматические проверки.

Verification не должна полностью заменять проверку разработчиком.

---

## Confidence

**Confidence** — степень уверенности Nodus в определенном знании или выводе.

Confidence необходим для отделения:

- подтвержденного факта;
- наблюдения;
- предположения;
- вывода модели.

Nodus не должен представлять предположение как подтвержденный факт.

---

## Question

**Question** — информация, которую Nodus не смог надежно определить самостоятельно и которую необходимо уточнить у разработчика.

Вместо того чтобы самостоятельно придумывать решение, Nodus может сформировать Question.

Например:

> Не удалось определить, почему компонент использует отдельный lifecycle вместо стандартного.

Questions могут впоследствии становиться частью Knowledge.

---

## Decision

**Decision** — зафиксированное архитектурное или инженерное решение проекта.

Decision отвечает не только на вопрос:

> Что сделано?

но и:

> Почему это сделано именно так?

Решения особенно важны в случаях, когда очевидного ответа из исходного кода недостаточно.

---

## Nodus

**Nodus** — система, объединяющая Knowledge, Context, Models, Tools и Verification для работы с существующим проектом.

Условный поток:

Project
↓
Knowledge
↓
Context
↓
Model
↓
Agent
↓
Tools
↓
Verification
↓
Updated Project / Knowledge

Nodus не является конкретной LLM и не является только Agent.

---

## Основная идея

Nodus должен стремиться не к тому, чтобы модель генерировала максимально много кода, а к тому, чтобы она:

1. понимала существующий проект;
2. использовала существующие решения как образцы;
3. учитывала проектные Policies;
4. явно показывала неопределенность;
5. могла задавать вопросы;
6. проверяла результат;
7. постепенно улучшала своё понимание проекта.

> Understand before you generate.
