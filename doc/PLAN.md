# Nodus Development Plan

Этот документ описывает последовательность развития Nodus от текущего состояния до первого рабочего прототипа.

План является живым документом и может изменяться по мере проверки гипотез и получения практического опыта.

Главный принцип:

> Сначала проверить гипотезу, затем усложнять систему.

---

## Phase 0 — Foundation

Цель: создать минимальный каркас Nodus и определить базовые границы системы.

- [ ] Создать базовую структуру проекта
- [ ] Определить основной runtime
- [ ] Определить интерфейс Model Adapter
- [ ] Определить базовый формат конфигурации
- [ ] Определить механизм логирования
- [ ] Определить базовую модель задачи
- [ ] Подготовить минимальный CLI / интерфейс запуска

Результат:

Nodus запускается и способен принять задачу и передать её выбранной модели.

---

## Phase 1 — Project Understanding

Цель: научить Nodus получать структурированное представление о существующем проекте.

- [ ] Индексация структуры проекта
- [ ] Поиск файлов и директорий
- [ ] Определение связей между файлами
- [ ] Создание File Understanding
- [ ] Хранение File Understanding
- [ ] Обновление File Understanding после изменений
- [ ] Определение релевантных файлов для задачи

Результат:

Nodus способен ответить на вопрос:

> Что представляет собой этот проект и какие его части относятся к текущей задаче?

---

## Phase 2 — Knowledge

Цель: создать слой явного знания о проекте.

- [ ] Определить формат Knowledge
- [ ] Поддержать описание компонентов
- [ ] Поддержать описание архитектурных решений
- [ ] Поддержать Examples
- [ ] Поддержать Policies
- [ ] Поддержать Questions
- [ ] Поддержать Decisions
- [ ] Добавить источник и степень уверенности для знаний
- [ ] Определить механизм обновления Knowledge

Результат:

Nodus способен использовать не только исходный код, но и накопленное понимание проекта.

---

## Phase 3 — Context

Цель: научить Nodus формировать релевантный контекст для конкретной задачи.

- [ ] Реализовать Context Builder
- [ ] Подбор релевантной Knowledge
- [ ] Подбор похожих Examples
- [ ] Подбор необходимых файлов
- [ ] Добавление Policies
- [ ] Добавление результатов предыдущих действий
- [ ] Контроль размера Context
- [ ] Возможность посмотреть, почему конкретная информация попала в Context

Результат:

LLM получает не весь проект, а контекст, необходимый для выполнения конкретной задачи.

---

## Phase 4 — Tools

Цель: дать Nodus возможность взаимодействовать с проектом.

Минимальный набор:

- [ ] Read file
- [ ] Search
- [ ] Write / Edit file
- [ ] Git diff
- [ ] Run command
- [ ] Run tests

Дополнительно:

- [ ] Получение статуса Git
- [ ] Анализ изменений
- [ ] Работа с проектными проверками

Результат:

Nodus способен не только отвечать текстом, но и выполнять действия в проекте.

---

## Phase 5 — Agent Runtime

Цель: реализовать цикл выполнения задачи.

- [ ] Передача задачи модели
- [ ] Обработка вызовов Tools
- [ ] Возврат результатов Tools модели
- [ ] Управление состоянием задачи
- [ ] Ограничение количества итераций
- [ ] Обработка ошибок
- [ ] Завершение задачи
- [ ] Возможность остановить выполнение человеком

Результат:

Nodus способен самостоятельно выполнять последовательность действий для достижения поставленной цели.

---

## Phase 6 — Verification

Цель: научить Nodus проверять собственную работу.

- [ ] Запуск существующих тестов
- [ ] Запуск TypeScript / compiler checks
- [ ] Запуск lint / project checks
- [ ] Анализ Git diff
- [ ] Передача результатов проверки обратно модели
- [ ] Повторная попытка после ошибки
- [ ] Ограничение количества попыток

Результат:

Nodus не заканчивает работу сразу после генерации изменений, а проверяет результат.

---

## Phase 7 — First Workflow

Цель: проверить Nodus на реальной задаче.

Первый сценарий:

> Добавление новой сущности в существующий проект по образцу уже реализованных сущностей.

Ожидаемый процесс:

- [ ] Получить описание задачи
- [ ] Найти похожие сущности
- [ ] Проанализировать существующие реализации
- [ ] Выбрать подходящий Example
- [ ] Сформировать план изменений
- [ ] Получить подтверждение разработчика
- [ ] Выполнить изменения
- [ ] Запустить проверки
- [ ] Исправить обнаруженные проблемы
- [ ] Показать итоговый diff

Критерий успеха:

Nodus способен выполнить значительную часть существующего процесса разработки, не нарушая принятые в проекте паттерны.

---

## Phase 8 — Learning Loop

Цель: проверить возможность постепенного накопления понимания проекта.

- [ ] Определять новое знание во время работы
- [ ] Предлагать обновление Knowledge
- [ ] Отличать факт от предположения
- [ ] Запрашивать подтверждение важных изменений Knowledge
- [ ] Обновлять File Understanding после изменений
- [ ] Сохранять полезные Decisions
- [ ] Сохранять повторяющиеся Patterns

Результат:

Каждая выполненная задача потенциально улучшает понимание проекта Nodus.

---

## Phase 9 — Model Independence

Цель: убедиться, что Nodus не привязан к конкретной LLM.

- [ ] Поддержать несколько Model Adapter
- [ ] Разделить общие Policies и model-specific настройки
- [ ] Определить различия поведения моделей
- [ ] Поддержать model-specific prompts / policies при необходимости
- [ ] Сравнить результаты разных моделей на одинаковых задачах

Результат:

Модель становится заменяемой частью системы, а не основой архитектуры Nodus.

---

# Первый MVP

Первый MVP не обязан включать все перечисленные этапы.

Минимальный рабочий контур:

Project
→ Project Understanding
→ Knowledge
→ Context Builder
→ Model
→ Tools
→ Verification

Главный тест MVP:

> Может ли Nodus взять новую задачу, изучить существующие реализации, выполнить изменения по образцу и проверить результат?

Если ответ отрицательный — дальнейшее усложнение системы не является приоритетом.

---

# Что намеренно не входит в первый MVP

Пока не являются целями:

- multi-agent архитектура;
- полностью автономная разработка;
- обучение собственной модели;
- сложная система памяти;
- полноценный IDE;
- поддержка большого количества LLM;
- автоматическое понимание всего проекта;
- автоматическое изменение всей Knowledge;
- универсальный AI-архитектор.

Эти возможности могут появиться позднее, если будут подтверждены соответствующие гипотезы.

---

# Критерий успеха Nodus

Nodus считается успешным первым экспериментом, если он позволяет разработчику выполнять типовую задачу быстрее и при этом сохраняет существующие архитектурные и инженерные подходы проекта.

Главный показатель:

> Не количество сгенерированного кода, а количество работы разработчика, которое удалось убрать без потери качества.
