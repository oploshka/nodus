# Происхождение Nodus

Этот документ фиксирует не текущую архитектуру Nodus, а причины появления проекта и исходные вопросы, из которых он вырос. Текущее устройство описано в `doc/architecture/`, а дальнейшая архитектурная эволюция — в `doc/history/evolution.md`.

## До Nodus: локальный coding-agent вокруг IDE

Формально история проекта началась не с Nodus как самостоятельного runtime. Первоначальный практический вопрос был существенно проще: как получить максимум от локальной coding-модели порядка до 40B в обычной разработке через WebStorm/Continue.

Раннее направление строилось вокруг идеи локального Cursor-like помощника. Базовая формула постепенно свелась к `LLM + tools + context + loop`: модель должна не только генерировать текст, а уметь искать по проекту, читать и менять файлы, запускать тесты и получать результаты обратно в следующую итерацию.

На этом этапе важными считались очень приземлённые operations:

```text
search -> read -> edit -> run tests -> observe -> retry
```

Причём уже тогда возникло важное ограничение: не передавать модели весь проект сразу. Сначала должен выполняться дешёвый поиск, затем чтение только нужных файлов, а короткие итерации и реальные логи должны быть предпочтительнее догадок модели.

Изначально предполагалось, что WebStorm/Continue будет UI и источником IDE context, а собственный agent runner — execution layer. Рассматривались `readFile`, `writeFile`, `search`, `runTests`, `runCommand`; собственный search был важен именно потому, что его можно контролировать и включать в execution loop, в отличие от одноразового IDE context.

## Cursor-lite как ранний архитектурный образ

До появления нынешней архитектуры направление несколько раз расширялось как условный `Cursor-lite`.

К простому loop последовательно добавлялись:

- top-k/RAG и project index;
- planning перед выполнением;
- memory/state, чтобы не повторять уже испробованные действия;
- multi-file reasoning и dependency-aware edits;
- error-aware retry loop;
- IDE context: открытые файлы, cursor и selection;
- live edit/preview через WebStorm plugin;
- persistent history и style hints.

В поздней ранней схеме это уже выглядело примерно как:

```text
WebStorm / Continue
        <->
local Node agent
  - LLM
  - tools
  - project retrieval
  - dependency graph
  - state
  - planning
  - iterative loop
```

То есть первоначальный проект стремился скорее к локальному IDE-агенту уровня Cursor-like workflow: модель видит editor context, строит план, выбирает релевантные файлы, редактирует несколько связанных файлов, запускает тесты и повторяет цикл.

Важно сохранить это как исторический контекст, а не как текущий roadmap. Значительная часть тех ранних сущностей была слишком быстро принята как готовое решение: RAG, dependency graph, persistent memory, IDE plugin и autonomous loop существовали скорее как предполагаемый комплект «что нужно агенту», чем как результат наблюдений за реальными failure modes.

## Почему направление изменилось

Со временем центр вопроса сместился. Стало недостаточно спрашивать «какие ещё возможности дать агенту». Более важным оказался вопрос: **какие решения вообще следует отдавать модели, какие операции должны быть детерминированными, и как runtime должен ограничивать дорогие или нестабильные действия модели**.

Именно здесь ранняя идея собственного orchestration оказалась важнее конкретного Cursor-like UI. Ещё в исходном обсуждении привлекательность собственного loop была связана с тремя свойствами: меньше скрытой магии, больше контроля и проще debugging. Это направление сохранилось, но стало самостоятельной архитектурной задачей.

Показательно и возвращение к очень ранней формуле `search -> read`. В первоначальном прототипе это были просто tools coding-agent. В современном Nodus та же идея появляется уже как bounded Worker retrieval: дешёвые operations должны закрывать навигацию и чтение проекта, не превращая каждый недостаток контекста в дорогой Research.

Поэтому нынешний Nodus нельзя считать просто следующей версией `Cursor-lite`. Скорее Cursor-like agent был первым конкретным сценарием, через который проявились более общие проблемы: orchestration, project understanding, controlled tool lifecycle, состояние выполнения, границы автономности и ограничения локальных моделей.

## Исходная проблема

Nodus не начинался с готовой схемы `Engine -> Planner -> Worker -> Research -> Edit -> Validation` и не создавался как попытка заранее спроектировать ещё один универсальный agent framework.

Отправной точкой было наблюдение за coding-моделями при работе с существующим проектом. Модель может понимать формулировку задачи и быть способна предложить разумное изменение, но реальная работа требует одновременно разбираться в конкретной кодовой базе, находить существующие решения, учитывать локальные соглашения и архитектурные ограничения, планировать работу, получать недостающую информацию, выражать изменения и проверять результат.

При этом высокая capability модели сама по себе не даёт ей знания конкретного проекта. Даже сильная модель может реализовать технически разумное решение, которое не соответствует существующей архитектуре, если в её контексте нет нужных примеров, ограничений, причин принятых решений или особенностей конкретной подсистемы.

Из этого появились две связанные линии исследования.

## Граница между моделью и runtime

Один из исходных вопросов Nodus:

> Какие части coding-задачи действительно требуют semantic reasoning модели, а какие надёжнее выполнять или контролировать программно?

Nodus не исходит из предположения, что существует заранее известное правильное разделение ответственности между моделью и runtime. Поиск этой границы является частью эксперимента.

Разные части задачи могут находиться в разных точках этой границы. Модель может владеть semantic решением целиком; runtime может только ограничивать её contract; модель может выражать intent, а runtime — материализовать его; некоторые полностью детерминируемые операции могут принадлежать runtime целиком.

Текущая архитектура появилась постепенно именно из таких переносов ответственности. Например, Edit эволюционировал от технических edit-actions около Worker к модели, где Worker сообщает semantic intent, а Engine владеет механикой изменения и commit. Это не считается доказательством универсальной границы — только текущим результатом экспериментов.

## Понимание конкретного проекта

Вторая исходная линия — Project Understanding.

Модель не должна каждый раз решать задачу так, будто перед ней неизвестный generic project. Для semantic решений ей могут быть нужны не только релевантные файлы, но и существующие реализации, проектные паттерны, ограничения, архитектурные решения, исключения и знания о том, как похожие задачи принято решать именно здесь.

Ранние концепты Nodus рассматривали Project Knowledge, task-specific Context, Policies, Patterns и Examples как способы постепенно накапливать и выбирать такое понимание. Значительная часть этой линии была отложена во время последующих runtime rewrite: прежде чем строить сложную систему знаний, проект сосредоточился на более приземлённых execution boundaries и реальных failure modes.

Сама проблема при этом не считается решённой или отвергнутой. Современный Research покрывает часть потребности в task-specific knowledge, но не является автоматически полной заменой более широкого Project Understanding.

## Ранние принципы

В ранней формулировке проекта появились несколько принципов, которые полезно сохранить отдельно от конкретных классов и архитектурных схем.

**Project first.** Существующий проект и его реальные решения важнее абстрактной «правильной архитектуры». Nodus не должен навязывать проекту новый стиль только потому, что модель считает его более привычным.

**Examples over rules.** Существующие реализации и повторяющиеся паттерны часто полезнее длинного набора общих инструкций. Жёсткие rules нужны там, где действительно существует ограничение, а не как замена пониманию проекта.

**Model agnostic.** LLM рассматривается как заменяемый компонент. Конкретный provider, размер модели или способ запуска не должны определять верхнеуровневую архитектуру Nodus.

**Uncertainty is information.** Если система не знает, почему принято решение, предположение не должно незаметно становиться project fact. Неопределённость должна оставаться видимой и при необходимости приводить к Research или взаимодействию с человеком.

**Human in the loop.** Изначальная идея не предполагала обязательную полную автономность. Человек рассматривался как отдельная control boundary для clarification, approval, conflict, risk и подтверждения знаний, а не как ещё один tool модели.

Эти принципы не означают, что ранняя реализация была правильной. Они фиксируют исходные ограничения на направление проекта и могут получать другую техническую форму по мере развития runtime.

## Локальные модели, но не только небольшие модели

Практическая разработка Nodus тесно связана с локальными моделями, в том числе с ограничениями доступного hardware, quantization и заметной разницей capabilities между моделями. На менее устойчивых моделях ошибки свободного agent loop проявляются особенно явно, поэтому они являются полезной средой для проверки архитектурных решений.

Однако Nodus не строится вокруг предположения, что его смысл существует только для небольших моделей. Более сильная модель тоже может выиграть от более надёжной execution mechanics и от лучшего понимания конкретного проекта. В таком случае выигрыш может проявляться не столько в способности вообще завершить задачу, сколько в качестве, предсказуемости и соответствии существующим принципам проекта.

Поэтому размер модели не является архитектурной границей Nodus.

## Что Nodus исследует

В наиболее общей форме Nodus исследует две связанные задачи:

1. где должна проходить граница ответственности между semantic reasoning модели и контролируемым runtime;
2. какой project-specific context нужен модели для тех semantic решений, которые остаются за ней.

Эти вопросы не имеют зафиксированного окончательного ответа. История проекта содержит несколько попыток провести границы иначе, часть abstractions была удалена, а некоторые ранние идеи позже возвращались в более простой форме.

Именно поэтому архитектура Nodus рассматривается как результат последовательных экспериментов и наблюдений за реальными failure modes, а не как реализация заранее выбранной финальной схемы.
