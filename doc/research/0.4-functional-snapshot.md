# Nodus 0.4 functional snapshot

Этот документ фиксирует отдельную research-задачу: восстановить функциональный снимок Nodus 0.4 и понять, какие полезные свойства были сохранены, изменены или потеряны при переходе к 0.5.

Это не план возврата старой архитектуры. Наличие механизма в 0.4 само по себе не является аргументом за его восстановление.

## Зачем нужен snapshot

Переход к 0.5 намеренно заменил значительную часть прежнего Planner/Worker lifecycle на schema-driven Core. Во время миграции часть старого кода была удалена или перестала быть активной, а часть полезной semantic policy осталась в prompts, response schemas, tests, history и старых implementations.

Перед дальнейшим удалением переходных артефактов полезно отдельно ответить на вопрос:

> какое наблюдаемое поведение 0.4 было ценным независимо от формы его реализации?

Результат исследования должен помогать развитию 0.5, а не диктовать её структуру.

## Baseline

Перед сравнением нужно выбрать конкретную последнюю рабочую точку 0.4: tag или commit, на котором production lifecycle ещё представлял согласованную 0.4-систему.

До выбора baseline не следует смешивать разные исторические состояния 0.4 в один воображаемый контракт.

## Что сравнивать

Минимальный список кандидатов для инвентаризации:

- Planner semantic policy, prompt guidance и response schema;
- task classification / Qualifier / bounded Determine, если они давали наблюдаемую пользу;
- Worker code/documentation behavior и правила continuation/retry;
- retrieval и Research behavior, включая bounded запросы и cache semantics;
- Edit ownership, task-local accumulated state, recovery/fallback и commit semantics;
- project-level verification (`EngineTest` / историческая Validation boundary);
- user-facing progress, diagnostic logging и Presentation semantics;
- task/execution statistics;
- model/language policy;
- tests и benchmark scenarios, которые фактически фиксировали полезное поведение.

Этот список — карта проверки, а не список обязательных features 0.5.

## Для каждого свойства

Для каждого найденного свойства зафиксировать:

1. **Наблюдаемое поведение** — что реально получал пользователь/runtime.
2. **Зачем оно появилось** — какой failure case или capability gap его породил.
3. **Где оно жило в 0.4** — код, prompt, config, test или runtime convention.
4. **Состояние в 0.5**:
   - сохранено;
   - сохранено в другой форме;
   - временно отсутствует;
   - намеренно отброшено;
   - пока неизвестно.
5. **Нужен ли эксперимент** — какой минимальный сценарий может показать, стоит ли возвращать поведение.

## PlannerTask и другие переходные артефакты

Текущий `automation/Step/Planner/PlannerTask/` не является активным Planner runtime 0.5, но его пока не следует удалять только потому, что он не подключён.

В нём и связанных исторических Planner implementations могут оставаться полезные:

- prompt guidance;
- response schema;
- decomposition semantics;
- ограничения против механического разбиения задачи;
- model request settings.

При создании настоящего Planner 0.5 можно использовать очевидно полезные части текущего `automation/Step/Planner`, но полную инвентаризацию 0.4 следует оставить этому research, чтобы не превращать текущий refactor в археологию старого runtime.

## Ожидаемый результат

Исследование должно закончиться небольшой таблицей решений, например:

| Capability | 0.4 behavior | 0.5 state | Evidence | Decision |
| --- | --- | --- | --- | --- |
| Planner semantic decomposition | ... | ... | scenario/test/history | keep / experiment / drop |

После этого только подтверждённые полезные свойства переходят в roadmap 0.5.
