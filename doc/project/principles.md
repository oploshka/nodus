# Принципы разработки Nodus

Этот документ фиксирует устойчивые инженерные ориентиры проекта. Это не описание текущей архитектуры и не набор абсолютных истин: конкретные runtime boundaries могут меняться по мере экспериментов.

## Project first

Решение должно учитывать конкретный проект, а не только generic correctness задачи. Существующие реализации, ограничения, соглашения и архитектурные причины важны так же, как формальная возможность реализовать изменение.

## Examples over rules

Когда поведение проекта лучше выражается существующими реализациями, предпочтительнее показать модели релевантные примеры, чем пытаться заранее превратить всё знание в большой набор абстрактных правил.

Это не отменяет explicit constraints там, где правило действительно устойчиво и важно.

## Uncertainty is information

Неопределённость не должна маскироваться выдуманным фактом. Если для semantic решения не хватает знания, это отдельное состояние, которое может привести к Research, уточнению, остановке или другому контролируемому действию.

## Model agnostic

Архитектура Nodus не должна предполагать конкретный размер модели или provider. Разные models и quantization могут иметь разные capabilities, но это входные свойства execution environment, а не определение проекта.

## Граница model/runtime проверяется экспериментом

Nodus не исходит из заранее известного ответа, какие части coding-задачи должны принадлежать модели, а какие runtime. Semantic reasoning, contracts, materialization, validation и control могут находиться в разных точках этой границы.

Перенос ответственности должен опираться на наблюдаемый failure mode или устойчивую инженерную причину, а не только на эстетически красивую архитектуру.

## Deterministic mechanics не обязаны принадлежать модели

Если операция может быть надёжно выполнена программно без потери semantic решения, её стоит рассматривать как кандидата на runtime ownership. Это не означает автоматического переноса любой операции из модели: граница проверяется на реальных задачах.

## Current project state authoritative

Persistent knowledge, cache, history и model observations не должны молча переопределять текущее состояние Project. Сохранённое знание может устареть и должно иметь понятную связь с источником и invalidation semantics.

## Human in the loop — отдельная boundary

Пользователь не является очередным tool модели. Clarification, approval, conflict resolution, risk acceptance и подтверждение знания относятся к отдельной control boundary. Конкретный interaction API пока может отсутствовать, но это различие важно сохранять архитектурно.

## Новая complexity должна иметь причину

Новая abstraction, Action, policy layer или subsystem не добавляется только потому, что она потенциально полезна. Предпочтительный путь: наблюдаемый failure/capability gap -> минимальная гипотеза -> проверка -> только затем устойчивый runtime contract.

## История ошибок ценнее иллюзии финального design

Nodus остаётся экспериментальным проектом. Удалённые abstractions и неудачные подходы полезно сохранять как причины решений, но не поддерживать ради compatibility с прошлой архитектурой.
