# Правила документации

Документация Nodus хранит не только описание кода, но и статус инженерного знания. Поэтому структура документации должна отделять текущее устройство проекта от планов, исследований и истории.

## Имена файлов

- Markdown-файлы называются в `lowercase-kebab-case.md`.
- `README.md` — единственное стандартное исключение и используется только в корне репозитория как точка входа.
- Внутри директорий не создаются локальные `README.md`; документ получает имя по своему назначению.
- Имена сущностей кода, API, protocol values и runtime identifiers не переводятся и сохраняются в форме, используемой проектом.

## Язык

Основной язык внутренней человеческой документации — русский. Английский сохраняется там, где он является частью кода, machine-facing contract, prompt, protocol value или устоявшегося технического термина.

Существующие английские документы не требуется переводить отдельной механической операцией: при содержательной актуализации соответствующий текст переводится на русский.

## Категории

- `doc/architecture/` — как Nodus устроен и работает сейчас.
- `doc/development/` — активные работы, roadmap и практики разработки/измерения.
- `doc/project/` — правила самого репозитория и разработки Nodus.
- `doc/history/` — прошлые состояния, сценарии и причины архитектурных переходов.
- `doc/research/` — гипотезы, эксперименты и направления, которые ещё не являются текущей архитектурой.

Ключевое правило: документ располагается по типу знания, а не только по подсистеме, к которой относится.

## Жизненный цикл знания

Типичный путь идеи:

```text
research -> development -> architecture -> history
```

Это не требует физически перемещать один и тот же файл на каждом этапе. Исследование может быть закрыто выводом и ссылкой на новый документ. Важно, чтобы читатель мог отличить гипотезу от принятого решения и текущей реализации.

## Research status

Research-документ должен в начале явно сообщать свой статус, если без этого идея может быть принята за текущий contract. Достаточно короткой human-readable отметки вроде `Статус: гипотеза`, `Статус: рабочий research-документ` или `Статус: эксперимент`.

Structured metadata (`evidence`, `implementation`, `last-reviewed`) добавляется только когда появится практическая потребность автоматически его обрабатывать. Не нужно превращать Markdown в registry заранее.

## Документация рядом с кодом

Архитектурные документы централизуются в `doc/architecture/`. Документ рядом с кодом допустим только когда он является локальной спецификацией или инструкцией, смысл которой непосредственно связан с этой директорией. Такой документ всё равно получает осмысленное имя, а не `README.md`.

## Актуальность

При изменении архитектурной границы нужно обновлять документ, который объявляет эту границу текущей. Исторические документы не переписываются под новое состояние, если их назначение — сохранить прошлый сценарий; вместо этого в них явно отмечается исторический статус.

Roadmap не должен дублировать подробную архитектурную документацию: он фиксирует состояние работы и следующие направления. Research-документы не должны формулировать неподтверждённую идею как уже принятую архитектуру.

## Автоматическая проверка

`npm run check:docs` выполняет минимальную механическую проверку документации:

- обычные `.md` используют lowercase kebab-case;
- вложенные `README.md` запрещены;
- локальные Markdown links не должны указывать на отсутствующий путь или выходить за пределы repository.

Эта проверка намеренно не пытается определять актуальность или истинность текста — semantic consistency остаётся частью review.
