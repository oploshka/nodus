# Nodus Architecture

Этот документ описывает концептуальную архитектуру Nodus.

Архитектура намеренно не привязана к конкретному языку программирования, LLM-провайдеру или инфраструктуре.

Главная задача архитектуры — разделить понимание проекта, формирование контекста, принятие решений, выполнение действий и проверку результата.

---

## 1. Общая модель

Nodus работает как слой между разработчиком, проектом и LLM.

Основной поток:

Developer
↓
Task
↓
Project Understanding
↓
Knowledge
↓
Context Builder
↓
Model
↓
Agent Runtime
↓
Tools
↓
Project
↓
Verification
↓
Result

При необходимости цикл повторяется:

Verification
↓
Result
↓
Model
↓
Tools
↓
Verification

---

## 2. Основные части системы

Nodus состоит из нескольких логических частей:

### Project

Исходный проект, с которым работает Nodus.

Содержит:

- исходный код;
- конфигурацию;
- зависимости;
- тесты;
- документацию;
- структуру проекта;
- другие доступные артефакты.

Nodus не должен изменять проект только ради получения дополнительного контекста.

---

### Project Understanding

Слой, отвечающий за структурированное понимание проекта.

Он работает непосредственно с существующими артефактами проекта и формирует информацию, которую можно использовать повторно.

Основной элемент:

**File Understanding**

Дополнительно могут существовать:

- понимание каталогов;
- понимание компонентов;
- связи;
- зависимости;
- Patterns;
- другие структурные сведения.

---

### Knowledge

Хранилище явного понимания проекта.

Knowledge отличается от исходного кода.

Исходный код показывает, **что существует**.

Knowledge может объяснять:

**почему это существует и как это следует использовать**.

Knowledge может создаваться:

- заранее разработчиком;
- во время анализа проекта;
- во время выполнения задач;
- после подтверждения разработчиком;
- на основе накопленных Decisions и Examples.

---

### Context Builder

Context Builder собирает информацию, необходимую для конкретной задачи.

Он определяет:

- какие Knowledge релевантны;
- какие Examples нужны;
- какие файлы необходимо прочитать;
- какие Policies применимы;
- какие результаты предыдущих действий важны.

Context Builder не обязан передавать модели весь проект.

Цель — получить достаточный контекст с минимальным количеством нерелевантной информации.

---

### Model Adapter

Model Adapter предоставляет унифицированный интерфейс для взаимодействия с LLM.

Он скрывает особенности конкретной модели или провайдера.

Условно:

Nodus
↓
Model Adapter
↓
LLM

Замена модели не должна требовать изменения основной логики Nodus.

При этом допускаются model-specific:

- prompts;
- policies;
- параметры;
- ограничения.

---

### Agent Runtime

Agent Runtime управляет выполнением задачи.

Он отвечает за цикл:

Task
↓
Model
↓
Tool Call
↓
Tool Result
↓
Model
↓
...

Runtime управляет:

- состоянием задачи;
- историей действий;
- вызовами модели;
- выполнением Tools;
- ошибками;
- ограничениями;
- завершением задачи.

Agent Runtime не должен содержать знания о конкретном проекте.

---

### Tools

Tools являются интерфейсом Nodus к внешнему миру.

Минимальный набор:

- Read;
- Search;
- Edit;
- Write;
- Git;
- Run Command;
- Test.

Tools должны быть максимально независимыми от LLM.

Модель принимает решение использовать Tool, но сам Tool выполняет определенную операцию.

---

### Verification

Verification проверяет результат выполнения.

Проверка может выполняться несколькими способами:

- тесты;
- компиляция;
- TypeScript checks;
- lint;
- project-specific checks;
- анализ diff;
- Policies;
- другие проверки.

Результат Verification возвращается в Agent Runtime и при необходимости передается модели для следующей итерации.

---

## 3. Knowledge и Project должны быть разделены

Это принципиальное разделение.

Проект является источником фактов.

Knowledge является интерпретацией этих фактов.

Например:

Project:

существует файл `EntityForm.tsx`.

Knowledge:

`EntityForm.tsx` отвечает за отображение формы редактирования сущности и используется как основа для аналогичных сущностей.

Если исходный код изменился, Knowledge потенциально становится устаревшей.

Поэтому Knowledge должна иметь возможность:

- обновляться;
- проверяться;
- помечаться как устаревшая;
- связываться с источником.

---

## 4. Knowledge не должна быть единственным источником истины

Nodus не должен слепо доверять сохраненному Knowledge.

При конфликте между Knowledge и текущим проектом необходимо учитывать актуальное состояние проекта.

Knowledge должна помогать модели быстрее понять проект, а не заменять проверку исходного кода.

---

## 5. Examples

Examples являются отдельным важным источником контекста.

Nodus должен уметь находить существующие реализации, похожие на текущую задачу.

Например:

Task:

> Добавить новую сущность.

Nodus:

1. находит существующие сущности;
2. анализирует их;
3. выбирает подходящие Examples;
4. использует их как основу контекста.

Это предпочтительнее генерации архитектуры с нуля.

---

## 6. Policies

Policies находятся между жесткими правилами и свободной генерацией.

Они описывают предпочтения проекта.

Пример:

> Если существует подходящий существующий механизм, предпочитать его созданию нового.

Policy не должна автоматически запрещать исключения.

Модель должна иметь возможность определить, что конкретная ситуация отличается от обычного случая.

---

## 7. Questions

Если Nodus не может надежно определить необходимое решение, он должен иметь возможность остановиться и задать вопрос.

Поток:

Task
↓
Analysis
↓
Insufficient Knowledge
↓
Question
↓
Developer
↓
Answer
↓
Knowledge / Context
↓
Continue

Это предпочтительнее уверенной генерации неправильного решения.

---

## 8. Decisions

Architectural и engineering decisions должны иметь возможность фиксироваться отдельно от текущего исходного кода.

Decision отвечает на два вопроса:

1. Что было выбрано?
2. Почему это было выбрано?

Decisions могут использоваться при формировании будущего Context.

---

## 9. Обновление Knowledge

После выполнения задачи Nodus может обнаружить новое знание.

Например:

- новый Pattern;
- новый Example;
- изменение архитектуры;
- новое исключение;
- новое решение.

Но автоматическое сохранение любого вывода модели в Knowledge не является обязательным.

Для важных изменений может потребоваться подтверждение разработчика.

---

## 10. Состояние выполнения

Каждая задача должна иметь собственное состояние.

Минимально оно может включать:

- Task;
- Context;
- Model interactions;
- Tool calls;
- Tool results;
- Changes;
- Verification results;
- Questions;
- Final result.

Это позволяет:

- продолжать выполнение;
- анализировать ошибки;
- повторять отдельные этапы;
- понимать, почему было принято решение.

---

## 11. Границы компонентов

Компоненты Nodus должны оставаться заменяемыми.

В частности:

Model
не должна знать о внутренней структуре Knowledge.

Knowledge
не должна зависеть от конкретной LLM.

Tools
не должны зависеть от конкретной модели.

Verification
не должна зависеть от конкретного Agent.

Agent Runtime
не должен содержать проектную архитектуру.

Это позволяет менять отдельные части системы независимо.

---

## 12. Основной цикл

Концептуально выполнение задачи выглядит следующим образом:

Task
↓
Understand
↓
Build Context
↓
Model
↓
Decide
↓
Tool
↓
Observe
↓
Verify
↓
Continue / Ask / Finish

Важно:

**Nodus не должен предполагать, что первое решение модели является окончательным.**

Модель может:

- запросить дополнительную информацию;
- использовать Tool;
- изменить решение;
- обнаружить ошибку;
- запросить помощь разработчика;
- завершить задачу.

---

## 13. Первый рабочий сценарий

Первая проверка архитектуры — добавление новой сущности в существующий проект.

Примерный поток:

Task
↓
Найти похожие сущности
↓
Изучить Examples
↓
Получить Knowledge
↓
Сформировать Context
↓
Предложить план
↓
Получить подтверждение
↓
Изменить проект
↓
Запустить Verification
↓
Исправить ошибки
↓
Показать итоговый diff

Этот сценарий должен стать первым полноценным интеграционным тестом архитектуры Nodus.

---

## 14. Что архитектура пока намеренно не определяет

На данном этапе не фиксируются:

- конкретный язык реализации;
- конкретный LLM provider;
- конкретная база данных;
- конкретная vector database;
- конкретный UI;
- конкретная IDE integration;
- конкретная система хранения Knowledge;
- multi-agent архитектура;
- способ долгосрочного хранения всех состояний.

Эти решения должны приниматься после проверки необходимости.

---

## 15. Основной архитектурный принцип

Nodus должен быть построен вокруг следующей идеи:

**LLM является заменяемым исполнителем, а понимание проекта, контекст, инструменты и процесс работы являются частью Nodus.**

Ценность Nodus должна сохраняться даже при замене используемой модели.
